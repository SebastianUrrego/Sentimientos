Análisis de sentimientos
1. Propósito del laboratorio
El laboratorio consiste en diseñar, comparar y desplegar un sistema de análisis binario de sentimientos sobre Sentiment140. El
trabajo se centra en justificar, mediante evidencia experimental, las decisiones de preprocesamiento, representación del texto y
clasificación que conforman el pipeline final.
El equipo partirá de dos referencias comunes, evaluará configuraciones bajo un mismo protocolo de validación cruzada, realizará
un análisis de ablación sobre la solución seleccionada y, al final, reentrenará el modelo con todo el conjunto de entrenamiento para
desplegarlo en A WS. MLflow se utilizará para registrar las comparaciones y mantener la trazabilidad entre ellas, la configuración
elegida y el modelo publicado.
Criterio general de evaluación. Se evaluarán el proceso experimental, la trazabilidad de los resultados, el funcionamiento
del modelo desplegado y el cumplimiento del contrato técnico definido en el Anexo A.
La guía fija los datos, el protocolo de comparación y la evidencia mínima que debe quedar registrada. El equipo conserva la decisión
sobre cómo implementar las transformaciones que se compararán: qué negadores preservar, cómo tratar alargamientos y emojis,
qué modelo spaCy usar, cómo obtener un vector por documento, qué hiperparámetros emplear y cuál será la configuración final.
El Anexo A reúne las convenciones y formatos exactos utilizados por la evaluación automática.
2. Protocolo experimental
Para que las comparaciones sean válidas, todas deberán utilizar el mismo conjunto de datos, la misma muestra y los mismos folds.
Dataset. Utilice exclusivamente el dataset de Hugging Face adilbekovich/Sentiment140Twitter, en la revisión indicada a con-
tinuación:
b6037e127257d95b9b23d31f78b264b9ebe697fd. Con la biblioteca datasets, cárguelo fijando esa revisión mediante load_dataset(...,
revision=...). En esta revisión, train contiene 1.360.000 registros y test 240.000; 0 corresponde a negative y 1 a positive. El
conjunto test se reserva para la evaluación final.
Muestra y folds. A partir de train, obtenga una muestra estratificada de 200.000 registros con semilla 42. Conserve el índice
original de train antes de muestrear o reindexar. Sobre esa muestra construya 3 folds estratificados, con mezcla aleatoria y semilla
42. La muestra y los folds se fijan antes de iniciar la experimentación y no podrán cambiar durante el laboratorio. Los equipos no
tienen que obtener exactamente los mismos 200.000 registros. Para la evaluación, protocol/partitions.csv es la referencia que
determina qué registros integran la muestra y en qué fold actúa cada uno como validación.
Métrica de comparación. Cada configuración se evalúa en los tres folds. Registre el Macro-F1 de cada fold, su promedio y la
desviación estándar poblacional ( ddof=0). Macro-F1 es el promedio del F1 de las clases negative y positive. Una configuración
debe conservar los mismos hiperparámetros en los tres folds.
Registro del protocolo. En MLflow, un run es una unidad de registro que puede contener parámetros, métricas, tags y artefactos.
Los runs que evalúan configuraciones se denominan aquí runs experimentales. Antes de ejecutar T0, B0 o cualquier otra confi-
guración, cree un único run destinado a registrar las condiciones comunes del protocolo experimental: dataset, muestra, folds e
integrantes. Este run no entrena ningún modelo; funciona como referencia para los runs experimentales posteriores. Los nombres
exactos de los parámetros y artefactos se especifican en A.2.
Referencias iniciales.
• T0: en cada fold predice la clase más frecuente en la porción de entrenamiento; en caso de empate predice negative.
• B0: convierte a minúsculas, sustituye URL y menciones por los tokens url y user, normaliza espacios, utiliza BoW con
unigramas y Logistic Regression. No aplica otras transformaciones. B0 utiliza los hiperparámetros por defecto de la biblioteca.
Si durante su ejecución aparece una advertencia de convergencia, no modifique sus hiperparámetros para eliminarla en B0
ni durante las comparaciones de preprocesamiento de la Sección 3; cualquier ajuste de hiperparámetros deberá evaluarse por
separado como una configuración adicional.
Evalúe T0 y B0 con el protocolo anterior antes de iniciar las comparaciones por etapas.

4. Selección y análisis de ablación
Una vez completadas las comparaciones obligatorias, seleccione un pipeline candidato con base en los resultados de validación
cruzada. El conjunto test no se utiliza para esta decisión.
Ablación. Revierta, una a la vez, las decisiones del candidato que difieren de B0 y mantenga fijo el resto del pipeline. Compare el
Macro-F1 de cada ablación con el del candidato. Por ejemplo, si el candidato utiliza TF-IDF con unigramas+bigrams y Linear SVM,
una ablación de la representación vuelve a la representación BoW de B0 sin modificar las demás decisiones.
A.4 define las seis decisiones que pueden someterse a ablación y la forma de registrar cada reversión. Si el candidato no difiere de
B0 en ninguna de ellas, no se exige ablación; si difiere en una, evalúe una; si difiere en dos o más, evalúe al menos dos.
Después de las ablaciones, el equipo puede mantener el candidato o elegir una configuración revisada. En el segundo caso, evalúe
esa configuración con los mismos tres folds y regístrela como EXTRA antes de definirla como final. No se exige una segunda ronda
de ablación.
5. Modelo final y análisis de errores
Después de seleccionar la configuración final, reentrene el pipeline con los 1.360.000 registros de train y evalúelo una sola vez
sobre los 240.000 registros de test. No ajuste la configuración a partir del resultado obtenido en test.
El run final deberá referenciar el run experimental que sustenta la configuración elegida y que cumple los requisitos del Anexo A.
Registre el modelo en MLflow Model Registry con nombre exacto sentiment140 y alias champion. El modelo registrado deberá
encapsular el preprocesamiento, la representación y el clasificador necesarios para recibir texto sin procesar y devolver la etiqueta
de sentimiento.

8. Evaluación automatizada y sustentación
La evaluación automática consultará la API, el Tracking Server y el Model Registry. Se verificarán las comparaciones obligatorias, la
correspondencia entre etapas y configuraciones, la consistencia aritmética de las métricas registradas, las contribuciones individua-
les, la procedencia en SageMaker y la trazabilidad del modelo desplegado. En particular, se comprobarán la media y la desviación
estándar poblacional de los tres folds y, cuando aplique, la métrica de ablación macro_f1_delta, definida en A.2:
/api/v1/predict ⟶ sentiment140@champion ⟶ run final ⟶ run experimental seleccionado.
Se utilizarán textos adicionales no publicados para calcular un Macro-F1 oculto mediante /api/v1/predict. Este componente
equivale al 15 % de la calificación. Su fracción de puntaje será:
𝑠 = clip ( 𝐹 1est − 𝐹 1𝐵0
𝐹 1ref − 𝐹 1𝐵0
, 0, 1 ) .
𝐹 1est es el Macro-F1 obtenido por el modelo del equipo sobre el conjunto oculto. 𝐹 1𝐵0 es el resultado del baseline B0 del evaluador
y 𝐹 1ref el de una configuración clásica de referencia sometida a las mismas restricciones, con 𝐹 1ref > 𝐹 1 𝐵0. Ambos valores se
publicarán antes de la ventana de evaluación; los textos y etiquetas ocultos no se publicarán. Igualar o superar 𝐹 1ref otorga el
puntaje completo de este componente.
El Macro-F1 oculto se calificará únicamente si el modelo puede trazarse hasta un run final válido y hasta sentiment140@champion.
El test_macro_f1 registrado por el equipo y el Macro-F1 oculto corresponden a conjuntos distintos y no tienen que coincidir.
Sustentación. notebooks/experiment_audit.ipynb se utilizará como apoyo y no forma parte del contrato de caja negra. Al
ejecutarse contra el Tracking Server deberá permitir reconstruir los runs, el protocolo y las contribuciones. Durante la sustentación
se podrá solicitar una modificación acotada. El uso de agentes de IA continuará permitido y el resultado podrá comprobarse mediante
pruebas adicionales.

A.3. Esquema de run/configuration.json
Todo run experimental y final registrará un JSON válido con exactamente tres campos de primer nivel: preprocessing,
representation y classifier, y dentro de ellos solo los campos definidos a continuación. No incluirá nombres de integran-
tes, timestamps, run IDs ni información ajena a la configuración efectiva.
• preprocessing: objeto con lowercase (boolean), url, mention, whitespace, stopwords, negators (lista), lemmatize (boo-
lean), elongation, elongation_spec, emoji, emoji_spec, resources (objeto) y additional (objeto). resources identifica
modelos, bibliotecas o recursos externos que afecten el preprocesamiento y sus versiones. additional describe cualquier
transformación adicional no representada por los otros campos.
• representation: objeto con type, ngram_range, library, library_version, spacy_model, spacy_model_version y pa-
rameters. parameters contiene los parámetros configurados explícitamente que afecten el representador. Si type=spacy_
embedding, deberá incluir document_vector_method como string no vacío.
• classifier: objeto con type, library, library_version y parameters. parameters contiene los hiperparámetros configu-
rados explícitamente. Los valores predeterminados no modificados quedan determinados porlibrary_version y no necesitan
expandirse.
Valores controlados.
• url, mention: keep, drop o token:<valor>;
• whitespace: keep o normalize;
• stopwords: keep, remove o remove_preserve_negation;
• elongation: keep o normalize;
• emoji: keep o text;
• representation.type: bow, tfidf o spacy_embedding;
• classifier.type: logistic_regression, linear_svm, sgd o most_frequent.
Campos no aplicables. Ningún campo obligatorio podrá omitirse. Cuando no aplique, elongation_spec, emoji_spec, spacy_
model y spacy_model_version serán null; resources, additional y parameters serán objetos vacíos {}. negators=[] salvo con
stopwords=remove_preserve_negation, cuando será una lista no vacía. elongation_spec será no nulo únicamente con elonga-
tion=normalize; emoji_spec, únicamente con emoji=text. Para bow y tfidf, ngram_range será una lista de dos enteros; para
spacy_embedding, será [] y parameters.document_vector_method será un string no vacío. Como referencia, son válidas des-
cripciones como reduce_repeated_chars_to_2, emoji.demojize o mean_token_vectors; son ejemplos ilustrativos, no valores
obligatorios. Para T0, preprocessing=null, representation=null y classifier.type=most_frequent.

Una decisión ablacionable se identifica mediante uno de estos seis valores exactos:
preprocessing.stopwords, preprocessing.lemmatize,
preprocessing.elongation, preprocessing.emoji,
representation, classifier.
Revertir una decisión significa devolver a B0 todos los campos que la forman y mantener sin cambio los demás. Para stopwords:
stopwords=keep y negators=[]; para lematización: lemmatize=false; para alargamientos: elongation=keep y elongation_
spec=null; y para emoji: emoji=keep y emoji_spec=null.
Revertir representation significa usar la forma de B0: type=bow, ngram_range=[1,1], campos spaCy en null, parameters={} y
los campos library y library_version iguales a B0. Revertir classifier significa type=logistic_regression, parameters={}
y los mismos valores de library y library_version que B0. Cambios de hiperparámetros dentro de un mismo representador o
clasificador no generan por sí solos una ablación obligatoria. El param ablation_reverted_decision usará uno de los seis valores
anteriores.
A.5. Contrato de la API
La API se implementará con FastAPI. Los endpoints JSON responderán con application/json. Los campos definidos son obli-
gatorios y pueden añadirse campos adicionales. En /audit/runs, params y tags reproducen strings de MLflow, metrics contiene
números y pueden aparecer tags de sistema adicionales. En endpoints especializados, los tipos JSON coincidirán con los definidos
aquí.
/api/v1/predict, /audit/model, /health y el alias champion deberán identificar el mismo run final.
Las listas de identificadores y rutas se ordenarán lexicográficamente, salvo predictions, que conserva el orden de entrada. Para
cálculos derivados se usará tolerancia absoluta 10−6. Si MLflow no está disponible, los endpoints /audit/* responderán HTTP 503
con detail=mlflow_unavailable; no reconstruirán respuestas desde una copia local.

Método y ruta Contrato
POST /api/v1/predict
Entrada JSON con text: un string o una lista de 1–32 strings; cada texto, máximo 1.000 caracteres. Salida HTTP 200:
model_run_id (string) y predictions (lista de strings negative o positive). Para un string, la lista tiene un
elemento; para un lote, conserva cantidad y orden. El modelo se resuelve desde sentiment140@champion.
GET /audit/protocol
HTTP 200 solo si existe exactamente un protocolo presentado. Devuelve protocol_run_id (string), dataset_id
(string), dataset_revision (string), sampling_strategy (string), sample_size (entero), random_seed (entero),
cv_strategy (string), cv_folds (entero), cv_shuffle (boolean), partitions_artifact (string) y members_artifact
(string). Las rutas serán exactamente protocol/partitions.csv y protocol/members.csv. Si no existe exactamente
un protocolo presentado: HTTP 409, detail=protocol_not_unique.
GET /audit/runs
Devuelve runs, lista ordenada por run_id. Cada objeto contiene run_id y status (strings), run_type (string, igual al
tag lab_run_type), params (objeto de strings), metrics (objeto de números), tags (objeto de strings), artifacts (lista
de strings) y configuration (objeto o null). Incluye todos los runs presentados, incluso incompletos. artifacts
enumera recursivamente las rutas de archivos, relativas a la raíz y en orden lexicográfico. Para el run de protocolo, o si
run/configuration.json falta o no es JSON válido en un run experimental/final, configuration=null.
GET /audit/contributions
Devuelve members (ordenada por member_id), invalid_run_ids y unattributed_run_ids. Cada miembro contiene
member_id, notebook_arn, run_ids, counted_run_ids, configuration_ids, stages y valid_configurations.
run_ids incluye runs experimentales válidos; counted_run_ids excluye T0/B0 e incluye los válidos que cuentan para
el mínimo; EXTRA puede incluirse. configuration_ids es la lista ordenada, sin duplicados, de los IDs en los runs
contados; valid_configurations es su cardinalidad. stages contiene, sin duplicados y ordenados, los valores de
lab_stage. El mínimo exige valid_configurations>=3 y al menos dos etapas. Los runs experimentales/finales
inválidos aparecen en invalid_run_ids; unattributed_run_ids contiene los que no pueden asociarse válidamente a
un par member_id/notebook_arn, y todo run no atribuible aparece también en invalid_run_ids.
GET /audit/model
Devuelve model_name (string), alias (string), version (entero), run_id (string), protocol_run_id (string),
selected_experiment_run_id (string), configuration_id (string), configuration (objeto), training_size
(entero) y test_macro_f1 (número). model_name=sentiment140, alias=champion. Si no existe el alias: HTTP 404,
detail=champion_not_found; si no se asocia a run final válido: HTTP 409, detail=champion_invalid.
GET /health
Resuelve sentiment140@champion y verifica inferencia. HTTP 200 si está disponible; HTTP 503 si no puede cargarlo o
resolverlo. Los cuerpos exactos aparecen en A.6.
Para /api/v1/predict son inválidos: ausencia de text, null, string vacío o solo espacios, lista vacía, más de 32 elementos, textos
de más de 1.000 caracteres, tipos distintos de string o una lista con algún elemento inválido. La solicitud completa producirá HTTP
4xx y no entregará resultados parciales. Una solicitud válida se completará en un máximo de 10 segundos.
